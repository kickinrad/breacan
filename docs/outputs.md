# Outputs

An output is a module that writes files from the kit's resolved tokens. Breacán has thirteen built-in outputs, and a project can add its own ([Modules](modules.md)). The config lists outputs in `preset` and `modules`, and sets each one's options under its name ([Configuration](config.md)).

| Output | Writes | Needs a kit |
| --- | --- | --- |
| [`dtcg`](#dtcg) | DTCG 2025.10 token files and a resolver | yes |
| [`css`](#css) | CSS custom properties | no |
| [`beer`](#beer) | a Beer CSS theme | no |
| [`design-md`](#design-md) | `DESIGN.md` in Google's format | no |
| [`claude-design`](#claude-design) | a Claude Design System artifact's files | yes |
| [`playground`](#playground) | a one-page kit viewer | yes |
| [`plugin`](#plugin) | an agent plugin for Claude Code and Codex | yes |
| [`rules`](#rules) | `breacan.rules.json`, the lint config | no |
| [`react-native`](#react-native) | a typed TypeScript module for React Native | yes |
| [`tailwind`](#tailwind) | a Tailwind v4 theme | yes |
| [`obsidian`](#obsidian) | Obsidian snippets for the Minimal theme | yes |
| [`mealie`](#mealie) | a Mealie colour file and overlay | yes |
| [`template`](#template) | the kit's own templates, filled in | yes |

An output that needs a kit fails without `kit` in the config.

## The generated header

With a kit, every generated text file starts with a header line. It names the engine, the kit and the output, and says not to edit the file:

```css
/* Generated by Breacán from ember 0.1.0, output css: do not edit; change the kit's inputs and rebuild. */
```

- The header goes on `.css`, `.js`, `.mjs`, `.ts`, `.kt`, `.md` and `.html` files. `.json` and other extensions get none.
- It goes after any front matter, doctype or `@charset`, and within the first 10 lines.
- An output that sets `lead: n` keeps its first `n` lines first, for a marker its reader looks for on line 1. The header follows them.
- A file that also holds hand-written text, such as `DESIGN.md`, gets no header.

`breacan check` fails a kit output when none of its first 10 lines matches `/^\W*Generated by \S+.*\bdo not edit\b/i`, and names the path. That is one line: comment marks, "Generated by <name>", then "do not edit". The systems guard reads the same rule. The code is `packages/core/src/header.mjs`.

## dtcg

`dtcg` writes the kit's resolved tokens as DTCG 2025.10 files that any tool reads.

- `<path>/<name>.tokens.json` holds the base mode.
- `<path>/<name>.<mode>.tokens.json` holds each other mode's differences.
- `<path>/<name>.<platform>.tokens.json` holds each platform's differences ([Platforms](platforms.md)).
- `<path>/<name>.resolver.json` ties the files into one document for Terrazzo, Swatchbook or another kit.

Aliases are resolved and each colour is a 2025.10 colour object. The Material component tokens the kit leaves alone are left out. Another project lists the base file after `builtin:material` in `include`, and each mode's file in `media` under its query.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | required | The folder to write. It must not be `tokens/`, the project's own source. |

## css

`css` writes CSS custom properties named from token paths.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | `src/styles/tokens.css` | The file to write. |
| `layer` | none | Wraps the declarations in this `@layer`. |
| `prelude` | none | Raw CSS written before the declarations. |
| `scheme` | none | The base mode's colour scheme, `"dark"` or `"light"`. |

A component's type role, such as `"label-large"` on an `md.comp` `*-font` token, becomes the five typescale variables it stands for.

**Modes.** With `scheme`, each colour that differs by mode becomes one `light-dark()` declaration on `:root`. `:root` also gets `color-scheme: <base> <other>`, so the page follows the system.

- `[data-theme="light"]` and `[data-theme="dark"]` set only `color-scheme`. That pins a mode on the root or on any element.
- A variable holding `light-dark()` resolves where it is used, so a pinned subtree switches without declaring anything again.
- A non-colour token that differs by mode keeps its `prefers-color-scheme` media block on `:root:not([data-theme="<base>"])`, and its value on each `data-theme` pin.
- `light-dark()` needs a Baseline 2024 browser: Chrome 123, Safari 17.5 or Firefox 120.

Without `scheme`, each other mode is a media block.

**Component tokens.** `css` writes Material's own component tokens, from `builtin:material` and untouched by the project, only where the `beer` output's rules read them. A component token the project or kit sets is always written. A platform that wants the full set builds it from `builtin:material` with its own output.

**Springs.** When the tokens hold Material's springs (`md.sys.motion.spring.*.damping` and `.stiffness`), each spring also gets a `-easing` variable, a CSS `linear()` curve, and a `-settle` time. `src/motion.mjs` makes them.

## beer

`beer` themes [Beer CSS](https://github.com/beercss/beercss) with the kit's tokens. Load it after Beer and the `css` output, and set the mode with `data-theme`.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | `src/styles/beer.css` | The file to write. |

It sets:

- a Beer variable for each of the kit's Material colour roles, as `var(--md-sys-color-<role>)`, since Beer names its colours after the roles;
- Beer's system variables (size, font, speeds, state layer, overlay) from Material's;
- the `label-large` type on buttons and chips;
- Material's values where Beer draws its own: the focus ring, slider handles, large buttons, rail, list and app bar (`src/web/material.css`);
- Material's panes inside Beer's `main` (`main > .panes`), with Material's breakpoints, pane widths and spacer (`src/web/layout.css`).

With a kit, Beer's `--font-icon` reads `<name>.typeface.icon`, and the opacity of its `--elevate1` to `--elevate3` shadows reads `<name>.elevation.shadow-opacity`. With either token absent, Beer keeps its own value.

## design-md

`design-md` writes [Google's DESIGN.md format](https://github.com/google-labs-code/design.md). It replaces only the front matter groups the format defines. The `name`, the `description`, other keys and the body stay as written.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | `DESIGN.md` | The file to write. |

On the role contract, it writes the colour roles by name, the fifteen type roles, the corners and the spacing scale. It adds a component for each on-colour pair, so `design.md lint` checks each pair's contrast. A file with no body yet gets one that states the usage rules. Off the contract, it writes the project's tokens by their names.

## claude-design

`claude-design` writes the kit as the files of a Claude Design System artifact. It writes `project/` under its `path`. Publish that folder to the kit's design-system artifact.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | required | The folder to write under. |

The artifact keeps its own index, `project/design-system.json`, with `"editing": "code"` so the page stays read-only. The output never writes the index. It uses the `css` and `beer` outputs. When the config lists them, they must come before it; when it leaves them out, it makes them in memory. It shows at most two modes.

| File | Holds |
| --- | --- |
| `README.md` | `<kit root>/notes.md` without its title, then each Material token the kit sets by hand with its description. The header is a Markdown link reference, which the page hides. |
| `tokens.json` | The page's list-shaped tokens: a theme per mode, every colour except Material's component tokens, the typescale as one type style each in Material's role groups, the corner scale, spacing and the state-layer opacities. Theme ids are the `data-theme` values of the `css` output's `scheme`, or else the mode names. |
| `tokens.css` | The same values, compiled the way the page compiles them. Its first line is the page's marker. |
| `components/bundle.css` | The type tokens' faces and Beer's icon face from Google Fonts, Beer CSS in its `beer` layer, then the `css` and `beer` outputs. |
| `components/bundle.js` | The kit's namespace and no code, since the components are Beer's markup. The page runs previews only beside one. |
| `components/<Name>/preview.html` and `README.md` | Each playground component specimen in its Material family. It loads Beer's script from jsDelivr at the version the engine was built with. The README links Beer's markup and Material's guidance. |
| `components/Cover/preview.html` | The cover: the kit's title and `tagline` beside the accent roles, as blocks cut by the corner scale. |

## playground

`playground` writes `index.html`, one page that opens from disk and shows the kit on its own generated theme. It uses the `css` and `beer` outputs, and `tailwind` if the kit has one. When the config lists them, they must come before it; `css` and `beer` are made in memory when left out.

```js
playground: { path: "docs/playground", examples: ["preview/example.json"] }
```

| Option | Default | Holds |
| --- | --- | --- |
| `path` | required | The folder to write. |
| `examples` | none | The project's own entry files, read at build and carried in the page. |

An example entry is `{ name, surface, output, preview?, captures?, devices? }`, with each path relative to the entry:

- `preview` is a live web page.
- `captures` is `[{ src, label, build? }]`, for a surface a page cannot embed.
- `devices` is `[{ name, width, height }]`.

A missing entry fails the build. A missing preview or capture fails `breacan audit`.

| File | Holds |
| --- | --- |
| `index.html` | Beer's stylesheet in a cascade layer, the kit's `css` and `beer` outputs, the kit's data and the engine's client as one script. The data is the name, version and title, the tokens the `css` output carries per mode, `notes.md` as HTML, and the examples. Beer's script and the icon face come from their CDNs. |
| `tailwind.html` | With a `tailwind` output: Tailwind's utility classes on the kit's outputs, in a frame so Tailwind's reset leaves Beer alone. |

**The page.** A navigation rail holds Foundations, Components, Cards, Pages, Examples (when there are entries) and Rules. Each destination is a list-detail layout at `#destination/item`. A top app bar has the kit's title and a mode switch. On small screens, the bar shows theme.toml's `icon` as the kit's mark, or `style` without one.

**Columns.** The Columns destination shows one specimen screen four times:

- **Base:** the Breacán-neutral base alone.
- **Theme:** the kit's own look.
- **Platform:** the platform's language alone, at Native.
- **Kit:** what the dial resolves for that platform at the kit's level.

A kit with `platforms` gets Platform and Kit, with a picker when it lists more than one. Without, it shows Base and Theme only. The mode switch moves every column. Each column is the same markup under its own CSS variables, written by the `css` output's code, and the columns stack on a phone.

The page holds the same Material component tokens as the `css` output. A mode's `data-theme` is the colour scheme its surface is nearer to, so the switch needs one dark and one light mode. `breacan audit` checks the page in a browser ([Check, audit and lint](check-and-lint.md#breacan-audit)).

## plugin

`plugin` writes the kit's agent plugin: one folder that Claude Code and Codex both install.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | required | The plugin's folder, such as `plugins/acme`. |
| `description` | "Build UI on the <title> kit: its rules, components and token names." | The manifest's one line. Set it when the kit's skill does more than build UI. |
| `repository` | none | A URL where the kit's files are. |
| `author` | none | The manifest's `{ name, email?, url? }`. |

The kit writes its own `skills/<name>/SKILL.md`, so its wording changes with the kit and needs no engine release. With none, the output starts one that points at the references and the lint. That starter has no header, since the kit then owns it. The output writes what the skill reads:

| File | Holds |
| --- | --- |
| `.claude-plugin/plugin.json` | The manifest: the kit's name, a description, `author`, `repository` and keywords. It has no `version`, so the runtime keys the plugin by its commit. |
| `skills/<name>/references/index.md` | The references below, each with what it is for. |
| `skills/<name>/references/DESIGN.md` | For a kit on the role contract: the roles, the components the contract pairs and the usage rules. |
| `skills/<name>/references/breacan.rules.json` | The lint config, for `breacan lint --rules <this file> <paths>` in the consumer's repo. |
| `skills/<name>/references/notes.md` | The kit's `notes.md`, its rules, when it has one. |
| `skills/<name>/references/components.md` | With a `beer` output: each playground component in its Material 3 family, with Beer's markup and Material 3's guidance where Material has a page. Without one: only the components Material 3 documents, with their guidance. |
| `skills/<name>/references/theme.toml` | The kit's `theme.toml` under a `#` header line, when it has one. |

The plugin guides an agent, and its rules file lets the agent's lint hold code to the kit. `breacan check` holds these files current with `notes.md`, `theme.toml` and the config. After `path` changes, the old folder stays until someone removes it. Files the output does not write, such as a kit's own evaluations beside the skill, stay the kit's.

## rules

`rules` writes the kit's lint config, which `breacan lint` reads in a consumer's repo ([Check, audit and lint](check-and-lint.md#breacan-lint)).

| Option | Default | Holds |
| --- | --- | --- |
| `path` | `breacan.rules.json` | The file to write. |

It holds every CSS variable the kit defines, each variable's usage rules and the tokens an import flagged for review. Usage rules come from the contract first, then from each token's own `$extensions["com.kickinrad.breacan"].usage`, which wins.

## react-native

`react-native` writes a typed TypeScript module for Expo or React Native. It needs a kit with two modes, the base and one media mode, and `builtin:material`.

```js
export default {
  modules: ["react-native"],
  include: ["builtin:material"],
  kit: { name: "acme" },
  "react-native": { path: "ports/react-native/tokens.ts" },
};
```

| Option | Default | Holds |
| --- | --- | --- |
| `path` | required | The file to write. It must end in `.ts`. |

The module exports:

- `tokens[mode]`, with the resolved DTCG paths as nested objects;
- `textStyles[mode]`, with Material's fifteen React Native `TextStyle` values;
- the `ThemeMode` and `ThemeTokens` types.

Mode keys come from `theme.toml`, such as `night` and `day`. Read a role as `tokens[mode].md.sys.color.primary`, a radius as `tokens[mode].md.sys.shape.corner.medium`, and a text style as `textStyles[mode]["label-large"]`.

**Values.**

- Dimensions become [unitless density-independent values](https://reactnative.dev/docs/height-and-width) for React Native layout.
- A `rem` dimension becomes 16 points per rem, the web's default root size, so a measure can stay in `rem` for the web.
- A dimension in `em` or `%` fails, because React Native has no parent size to resolve it against.
- Durations become milliseconds, and colours stay strings.
- Font stacks become their first family. Install the named fonts in the app.
- CSS shadows, aggregate typography tokens and untouched Material component defaults are left out. Named type styles are in `textStyles`.

**Platforms.** When the kit lists platforms, the module also exports `themes[platform][mode]`, `ThemePlatform` and `Theme`. Each theme holds its own `tokens` and `textStyles`. The listed platform keys and both mode keys are TypeScript types. An app can pick a platform like this:

```ts
const platform = Platform.select({ ios: "ios", android: "android", default: "android" });
const theme = themes[platform][mode];
```

A kit without `platforms` gets no `themes`, `ThemePlatform` or `Theme`.

## tailwind

`tailwind` writes one Tailwind v4 `@theme inline` file. It maps Tailwind's namespaces onto the kit's runtime CSS variables.

| Option | Default | Holds |
| --- | --- | --- |
| `path` | required | The file to write. |
| `css` | required | The runtime CSS file, which the header names. |

## obsidian

`obsidian` writes a snippet per mode for Obsidian's Minimal theme, code colours included, as `<out>-<mode>.css`.

| Option | Default | Holds |
| --- | --- | --- |
| `out` | required | The path and file stem to write. |

- The monospace face is the theme's `mono`.
- Minimal's hue slots come from Material's accents and the kit's colour roles named for the other hues: `<name>.color.orange`, `yellow`, `green` and `cyan`. A slot the kit lacks stays Minimal's.
- The third text tier and the strong border take the kit's `on-surface-muted` and `comment` roles, or else Material's `outline` and `outline-variant`.

## mealie

`mealie` writes `<out>.env`, with Mealie's colour slots, and `<out>.css`, a full-look overlay.

| Option | Default | Holds |
| --- | --- | --- |
| `out` | required | The path and file stem to write. |

It reads theme.toml's `[mealie]` table:

- `slots` and `overlay` map Mealie's seven slots (`primary`, `accent`, `secondary`, `success`, `info`, `warning` and `error`) to one palette colour each.
- `stars` names the rating stars' colour.

Mealie's five layers are the palette colours of Material's `surface`, `surface-container-low`, `surface-container`, `surface-container-high` and `surface-container-highest`. Its text is `on-surface`'s colour, and its quieter text is `on-surface-variant`'s. Each must be one palette colour in both modes.

## Shared rules for tailwind, obsidian and mealie

These three read the kit's name and `VERSION`. The kit's token prefix is its name, and the title is the theme's. The base mode comes first and the other mode second, with the theme's mode names capitalised. `tests/outputs/` is a small kit with golden files for all three.

## template

`template` writes a kit's own files for apps Breacán has no output for, such as terminal and editor themes.

```js
template: { from: "templates", to: "ports" }
```

| Option | Default | Holds |
| --- | --- | --- |
| `from` | required | The folder of templates. |
| `to` | required | The folder to write. |

Every file under `from` is written to the same path under `to`.

- `{{<mode>.<colour>}}` becomes that mode's palette colour as `#rrggbb`, so `{{night.blue}}80` adds an alpha.
- `{{name}}` becomes the kit's name.
- Every other byte stays as written.

A slot the theme lacks fails the build and names the file. CSS, JS, Kotlin, Markdown and HTML files get the generated header. Other formats are written as the template has them.
